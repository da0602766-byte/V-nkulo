# APK — etapa 1: diagnóstico e base para evolução

Data: 27/09/2026. Escopo autorizado: levantamento técnico, baseline possível, arquitetura e processo de geração. Não implementa as etapas 2–7. A investigação disponível foi concluída; baseline físico Android permanece pendente e explicitamente não foi substituído por teste desktop.

## Resultado

O APK 1.7.1 publicado corresponde ao artefato auditado e ao build Android registrado no GitHub. A fonte está preservada em branch própria, ainda não integrada à principal. O principal obstáculo ao offline é a dependência da página inicial/autorização/renderização remota, seguida da ausência de banco operacional e protocolo de sincronização no aparelho.

Recomendação: manter React/TypeScript, criar entrada mobile cliente empacotada e introduzir armazenamento/sincronização nativos progressivamente. O desenho, os contratos e a matriz de módulos estão em [APK_OFFLINE_ARQUITETURA.md](../coordenacao/APK_OFFLINE_ARQUITETURA.md).

Nenhum código de execução do sistema, APK, credencial, banco ou configuração foi alterado. Foram adicionados documentação e um diagnóstico CLI somente de leitura. A navegação autenticada usa o funcionamento normal do site, que pode registrar presença/atividade; não foram submetidos formulários, mensagens ou mudanças administrativas.

## Processo de geração comprovado

Workflow versionado: `.github/workflows/build-vinkulo-apk.yml` no commit Android identificado. A validação original usa Ubuntu, Temurin JDK 17, Gradle 8.10.2, Android Gradle Plugin 8.7.3, Google Services plugin 4.4.2 e compileSdk 35.

Segredos esperados pelo workflow, cujos valores não foram acessados: `ANDROID_SIGNING_KEYSTORE_BASE64`, `ANDROID_SIGNING_PASSWORD` e `VINKULO_GOOGLE_SERVICES_JSON`. O keystore é decodificado no diretório temporário do runner; a configuração Firebase vai para `app/google-services.json`, não versionado. O Gradle release exige os parâmetros de assinatura.

Passos reexecutáveis no ambiente de CI já configurado, a partir do mesmo commit:

```text
gradle testDebugUnitTest lintRelease assembleRelease
apksigner verify --verbose --print-certs app/build/outputs/apk/release/app-release.apk
comparar o certificado com public/downloads/VINKULO_ANDROID_1.5.1.apk
conferir SHA-256 e arquivar APK, relatórios e mapping.txt
```

O workflow pode ser acionado manualmente na branch Android ou por alteração elegível da PR. Não acionar na principal esperando obter o fonte 1.7.1 antes de integrá-lo. Uma reexecução deve resolver os segredos exclusivamente pelo CI; jamais copiar uma chave privada para a documentação ou para o diagnóstico.

Limitações: não há Gradle Wrapper versionado; dependências não têm lock/verificação de checksums no conjunto auditado; actions usam tags e runner `ubuntu-latest`. O pipeline é rastreável e já funcionou, mas não há garantia de APK bit a bit idêntico em uma recompilação futura. Antes do primeiro novo APK, fixar/verificar ferramentas e dependências, além de conferir requisitos de distribuição vigentes.

## Baseline obtido agora

### Navegador autenticado — observação de tela

Brave desktop, sessão existente, viewport observado 1265 × 615, rede do computador sem limitação artificial. Uma navegação de preparação por tela, seguida de três recarregamentos na mesma aba. Cache não foi limpo. Usuário/comunidade não foram trocados. A aba original do usuário ficou preservada; a aba de diagnóstico foi fechada.

Método: relógio de parede antes de `reload`, tempo até retorno da navegação e depois até o marcador de UI observável. Mural: heading “Feed da comunidade” visível e “Atualizando…” ausente. Pedidos: heading “Meus pedidos” visível. Pessoas: busca “Buscar pessoa” visível. Esses marcadores não provam carregamento de todos os módulos auxiliares. Os valores incluem comunicação/observação da ferramenta; não são LCP, INP, TTFB ou tempo puro de renderização. A API de automação não expôs Performance API; nenhum número dessa API foi inventado.

### Android e rede degradada — não medidos

Não foram encontrados `adb`, emulador ou Android SDK no PATH, nas variáveis Android e nos diretórios locais padrão inspecionados. Java disponível no PATH é JRE 8, insuficiente para o build JDK 17 do projeto. Não foi estabelecida conexão com aparelho; isso não afirma que o usuário não possui celular/SDK em outro local.

Permanecem sem número: abertura fria/retomada reais do APK, memória PSS, quadros lentos, bateria, tráfego móvel, modo avião, 3G instável e encerramento pelo Android. O relatório de arquitetura contém protocolo e orçamentos propostos. A etapa 2 pode iniciar a preparação técnica, mas esses ensaios são um gate antes de alegar ganho Android ou distribuir amplamente a nova arquitetura.

## Achados que orientam a implementação

| Prioridade | Achado | Consequência / ação prevista |
| --- | --- | --- |
| P0 | Painel depende de render/autorização remota | Entrada cliente empacotada, bootstrap e autorização offline específica |
| P0 | Não existe outbox operacional/idempotência geral para cliente offline | Contrato de escrita versionado, recibo atômico e fila local transacional |
| P0 | Fonte Android distribuído está em PR não integrada | Preservar ref e validar integração antes da primeira evolução nativa |
| P0 | Troca de conta/comunidade exige isolamento também no aparelho | Banco/ponte por contexto, expiração, bloqueio e política de pendências |
| P1 | `local-media.ts` guarda blobs sem escopo de conta/comunidade/expiração no registro | Projetar nova política de dados locais e migração; não declarar o armazenamento atual cifrado/isolado |
| P1 | Scripts/estilos priorizam rede, navegação retorna tela offline | Não transformar HTML autenticado em cache compartilhado; criar versão coerente dos recursos locais |
| P1 | Feed inicial é revalidado e módulos fazem chamadas próprias | Medir chamadas/renderização antes de consolidar carregamento; preservar frescor e autorização |
| P1 | Algumas leituras podem ter efeitos de manutenção | GET de visitantes chama reconciliação de categorias; protocolo incremental deve ter contrato próprio e testar efeitos, não reproduzir cegamente todas as rotas |
| P1 | Documentos antigos divergem de armazenamento atual | Chat D1/retenção semanal e anexos bucket devem orientar a cópia offline; revisar textos antes de ativar novo armazenamento |
| P1 | Falta ambiente Android conectado | Coletar baseline nativo e homologar atualização sem desinstalação/perda de dados |

Nenhum desses itens foi corrigido silenciosamente na etapa de diagnóstico. A matriz por módulo e os critérios de conflito/retenção estão no documento de arquitetura.

## Repetir o diagnóstico

```bash
node scripts/apk-baseline.mjs
node scripts/apk-baseline.mjs --online
```

O modo padrão não faz rede. O modo online consulta somente o domínio oficial fixo, sem credenciais, e compara o APK da versão encontrada no fonte local. Imprime JSON; não cria arquivos nem registra corpos/cookies. Um status inesperado, falha de transporte ou divergência de APK retorna código 1; uso inválido retorna 2. Checkouts sem fonte Android podem usar o modo local, mas não afirmar correspondência de publicação sem resolver a fonte/versão.
