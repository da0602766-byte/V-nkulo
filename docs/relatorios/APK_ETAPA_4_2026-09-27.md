# APK — etapa 4: rascunhos e fila de visitantes

Autorizada pelo proprietário após a publicação da etapa 3 (Sites 321).
**Em implementação e validação. Não considerar o APK 1.10.0 publicado.**

## Recorte entregue pelo código

- Formulário básico no leitor local existente: nome, telefone/e-mail opcionais e data de entrada. Campos administrativos, classificação, observações pastorais, vínculos e anexos continuam no cadastro online; não copiar diretório de pessoas.
- Salvar rascunho é explícito. A interface só informa sucesso após confirmação do armazenamento nativo. Campos ainda não salvos são limpos ao ocultar a tela, com orientação visível para salvar antes de sair. Não confundir formulário digitado com trabalho persistido.
- Room/schema 2 existente: um registro AES-GCM representa rascunho e operação; transição para fila troca o estado no mesmo registro, mantendo UUID e payload. Conta/comunidade fazem parte do escopo criptográfico. Limite global de 200 registros operacionais mais a concessão; sem exclusão automática de trabalho pendente.
- Consentimento separado das consultas. Concessão `visitor.create` por até 8h, sessão atual e identificador aleatório da instalação; token opaco de 256 bits, guardado somente cifrado no aparelho e por HMAC no servidor. Nenhum token/cookie passa à ponte JavaScript. O servidor exige **também** a sessão/cookies próprios atuais e reavalia a permissão `visitors.create` a cada requisição. Não é um token genérico para outras APIs.
- `POST /api/mobile/write-bootstrap` e `POST /api/mobile/visitors`, cliente `android-write-1`. Origem restrita, desafio na preparação, corpo JSON limitado por bytes, campos permitidos e datas reais. Acessos temporários/feed-only não habilitam escrita offline.
- UUID por conta/comunidade + HMAC do payload + resultado/ID do visitante são persistidos na mesma transação D1 que cria visitante e auditoria. Repetir UUID/payload devolve recibo; UUID com payload diferente é recusado. Duplicidade por nome/e-mail/telefone na própria comunidade devolve conflito, sem expor fichas semelhantes pelo novo endpoint. Não altera a API de cadastro online existente.
- WorkManager exclusivo, conectividade obrigatória, tentativas com backoff exponencial/jitter; `Retry-After` respeitado quando fornecido. Reserva de envio abandonada vence em 2 minutos. Erros de rede conservam UUID/payload; 401/403 bloqueiam até nova preparação. 409/422 ficam visíveis, sem sobrescrita automática. O Android não garante horário de execução em segundo plano.
- Logout/bloqueio/troca de contexto impedem novos envios; uma requisição já aceita não pode ser desfeita pela saída. O recibo permanece recuperável após reautenticar a mesma conta/comunidade. Não é permitido apagar uma operação de resultado ainda incerto. Remover recibo local confirmado não apaga visitante do servidor.

## Banco e recuperação

Migração aditiva 0081: `mobile_write_grants` e `mobile_visitor_receipts`; não modifica visitantes existentes. Para bases hospedadas anteriores, o bootstrap autenticado executa o mesmo `CREATE TABLE IF NOT EXISTS`. Nenhuma credencial, fixture ou cadastro de teste é inserido em produção para homologação.

Recibos do servidor não são purgados automaticamente: removê-los reabriria a possibilidade de repetição antiga. Eles não contêm contato/nome/payload aberto. Exclusão da conta/comunidade remove por FK. Token expirado é limpo durante nova preparação; revogação de sessão é conferida em todo envio, mesmo se a linha da concessão ainda existir.

## Evidências e pendências

- Testes novos em SQLite: idempotência, perda de resposta, rollback, duplicidade, isolamento, entrada inválida/quota, concessão/expiração e revalidação real de papel via Worker compilado.
- Runtime Workers/D1 local: transação real, `changes()`/`last_insert_rowid()`, repetição sem segundo cadastro/auditoria e rollback após falha de auditoria aprovados.
- Pré-publicação final do backend: **535 testes web aprovados**, tipos/build/artefato aprovados, lint 0 erros/46 avisos. Sete testes novos incluem runtime D1 real e permissão real no Worker compilado. A suíte anterior, com menos dois testes, havia aprovado 533.
- CI Android e testes instrumentados de rascunhos/fila/interface: em andamento. Homologação física com sessão real, modo avião, morte do processo e políticas de bateria do fabricante permanece necessária antes de distribuição geral. Não há ganho percentual de desempenho medido.
- Etapa 5 não autorizada. Download geral continua 1.7.1; candidatos 1.8.0/1.9.0 mantidos para rastreabilidade. Uma atualização Android ruim deve ser corrigida com versionCode maior, não sugerir desinstalação/downgrade com pendências.
